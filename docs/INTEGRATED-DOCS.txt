# Atlas Chat

**Local-first AI desktop application evolving toward a hybrid AI platform.**

> Project status: active development / pre-release. Feature maturity and deployment status vary by subsystem. See the internal project master document and evidence register before treating any capability as production-ready.

## Vision

Atlas aims to make capable AI systems more accessible beyond centralized datacentres by combining local model inference, tool use, agent orchestration, observability and an extensible ecosystem. The desktop application is the user-facing foundation; the longer-term direction includes optional distributed compute and commercial services.

## Product direction

- Local-first desktop experience and model access.
- Hybrid operation: local models with optional remote services where explicitly enabled.
- Multi-agent orchestration, task execution and operational visibility.
- Model Context Protocol (MCP) integrations and extensible tools.
- Developer workflows, knowledge features and persistent conversations.
- A future ecosystem for nodes, contributors, integrations and commercial services.

## Architecture (documented design)

- **Frontend:** React, TypeScript, Vite.
- **Desktop shell:** Tauri and Rust.
- **Compatibility/backend layer:** existing Python chat server and services.
- **AI runtime:** llama-swap and local model endpoints.
- **Agent/platform components:** Atlas Node, Operations, MCP, Dev Engine and a Rust control-plane workstream.

The existing Python-served chat experience is to be preserved and integrated with the desktop shell rather than casually replaced. Atlas Desktop and Atlas Online are separate product surfaces and should remain architecturally distinct.

## Local development environment

Previously recorded model aliases: `assist`, `coder`, `mentor`, `mentor-dense`, `tasks`.

These are historical environment notes, not universal defaults. Consult local configuration before launching services.

## Development principles

1. Inspect the current implementation and dependencies before changing code.
2. Plan the complete feature and identify affected components.
3. Integrate related changes coherently rather than stacking disconnected patches.
4. Preserve user data, settings, chat history, model files and Git metadata.
5. Test the changed subsystem, then run regression/integration tests and production build checks.
6. End with end-to-end runtime validation on the target machine.
7. Report source-complete, test-passing, build-passing and runtime-verified as separate states.
8. Keep rollback paths and record exact release artifacts and hashes.
9. Track only processes Atlas owns; never terminate unrelated user processes.
10. Keep security-sensitive actions scoped, approved and auditable.

## Current known workstreams

- Desktop shell, launcher, installer and in-place upgrade lifecycle.
- Chat reliability, conversation queue and conversation navigation.
- MCP tool loop, approval and audit behaviour.
- Atlas Node and control-plane foundations.
- Operations dashboard and agent observability.
- Local Dev Engine and sandboxed patch workflow.
- Knowledge Library and conversation import.
- UI polish, bot avatars and usability improvements.

See `docs/PROJECT-MASTER.md`, `docs/DEVLOG.md` and `docs/EVIDENCE-REGISTER.md` for status and caveats.

## Build and release

Build instructions have changed across iterations. Use the current checked-in build scripts and the latest Windows build handoff rather than assuming old commands remain valid. A successful frontend build alone does not mean the Rust desktop application or installer is release-ready.

## Security and privacy

Atlas is designed around local-first operation and explicit control over remote execution. Do not describe the product as fully offline, fully private, secure-by-default or production-hardened without validating the exact configuration and threat model. Remote workload participation and privileged actions require explicit consent and scoped authorization.

## Project status

Atlas is an active engineering project. Some subsystems have staged implementations and automated test evidence; target-Windows runtime acceptance remains necessary for several features. The conversation queue and open-conversation cancellation/navigation issues reported on 8 November 2026 remain active blockers until reproduced and verified fixed.

# Atlas Chat: rules for every Claude session

Read this before any work. It exists because of a real mistake (2026-11-10, see the end).

## 1. Which app is the real one
- The real app is the **desktop app**: `atlas-rust-desktop/` (Tauri + Rust shell, React frame).
- The backend and chat UI that **ship in the installer** are in
  `atlas-rust-desktop/src-tauri/resources/atlas/` (`server.py`, `index.html`, `books.py`, ...).
  **Change these files.** The files with the same names in the repo root are older copies.
- Jason builds with `.\build-release.ps1`, then runs the installer that the build prints.
  He starts the app from the Start menu ("Atlas Chat"). He does NOT start it with `python app.py`.
- A branch that has no `atlas-rust-desktop/src-tauri/tauri.conf.json` is an OLD version of Atlas.
  `main` is one of them (as of 2026-11-10). Never build on it. Never send Jason to it.

## 2. Before you write any code
1. `git fetch origin`, then list branches by date:
   `git for-each-ref --sort=-committerdate --format="%(committerdate:short) %(refname:short)" refs/remotes`
2. Find the newest branch that holds the desktop app. Build on that one.
   If Jason names another branch or file, check it against step 1 and tell him when it is older.
3. A `HANDOFF.md` only describes its own branch. Old branches hold old handoffs. Check the date and the branch.
4. If you are unsure which branch Jason runs, ask him for the output of `git status -sb`. Ask first.

## 3. How to give Jason your work
- Build on top of his app branch, so that his branch can fast-forward to yours.
- Then he runs ONE command in `F:\APP-DEV\projects\atlas-chat`:
  `python get_update.py <your branch>`
  It checks first, refuses old branches, never switches branch, and prints the next steps.
- **Never tell Jason to run `git checkout <branch>`, `git switch`, `git reset` or `git pull` on another branch.**
- Never push to `main` or to his app branch without his clear yes.

## 4. How to write to Jason
- Checks and warnings come FIRST, before the steps. Never after.
- First line: one action. Numbered steps. One action per step. Short common words.
- Say plainly what is tested and what is not. "Tests pass in the cloud" is not "works on the PC".
- Do not say "you are missing nothing" unless you compared his branch with every remote branch.

## 5. Tests
- Backend (run in `atlas-rust-desktop/src-tauri/resources/atlas`):
  `python -m unittest discover -s ../../../validation-tests -p "test_*.py"`
- Repo root: `python -m unittest discover tests`
- Bundle check (also run by the build): `python check-bundle.py`
- Known before 2026-11-10: `validation-tests/test_knowledge_library.py` fails at import (stale stub),
  and `tests/test_conversation_api.py` has 1 error in the cloud. Do not count these as your breakage, do not hide them.

## 6. Standing rules (from HANDOFF.md)
- Never send emails. Never delete files outside atlas-chat. Client installs use normal (non-abliterated) models.
- Accessibility: keyboard access, visible focus, reduced motion, works at phone width.
- Jason's data (chats, bots, library) lives outside git. Never reset or overwrite it.

## 7. Install folders on Jason's PC (checked 2026-11-11)
- **Live install:** `F:\APP-DEV\projects\atlas-chat\app`. The Start menu shortcut "Atlas Chat" points to `app\atlas-desktop.exe`.
  The installer defaults to it (`nsis/f-drive-only.nsh`). No F: drive: `%LOCALAPPDATA%\atlas-chat\app`.
- **Old install (before 2026-11-10):** `F:\APP-DEV\projects\atlas-chat\Atlas Chat`. Do not use it. Do not edit it.
  Jason renames it to `Atlas Chat.old` and deletes it later. Never tell him to run its `uninstall.exe`:
  both installs share one app ID, so it may remove the shortcut and registry entry of the live install.
- The install folder is a **copy** of `src-tauri/resources/atlas` plus `atlas-desktop.exe`. Never edit files inside it.
  The build overwrites it. Edit the source in `atlas-rust-desktop/`.
- Data is outside the install: `F:\APP-DEV\data\Atlas Chat`. Folders `data`, `bots`, `exports`, `logs`, `runtime`,
  `swarm-workspaces`, `swpr`, `swr-user testing`, `vnc-workspace` in the project folder are Jason's work. Never delete them.
- Safe to delete (the build recreates them): `atlas-rust-desktop/node_modules`, `dist`, `src-tauri/target`, `__pycache__`.

## What went wrong on 2026-11-10
Jason pointed a cloud session at `HANDOFF.md` on `claude/intelligent-bohr-9laqiq`. That branch came from the old
Python app. The session built book import there without looking at the other branches, then told Jason to
`git checkout` its branch and said he was missing nothing. His project folder switched to the old app.
`git checkout -` put it back. Book import was then rebuilt inside the desktop app. Sections 1-4 prevent a repeat.

## What worked

## What failed (do not repeat)
- huggingface_hub froze on qwen3-14b at 3.44 GB. Use curl.exe -fL -C - with --retry.
- curl without -f wrote a 0-byte file on a wrong file name (bartowski files start with "huihui-ai_").
- --no-mmap: removed in this llama.cpp build -> llama-server exits, llama-swap returns 500. Use --load-mode none.
- --fit (default on) + --fit-target: wrong both ways on Vulkan/Windows. It over-filled VRAM before, and now (desktop apps
  using 3.9 GB) it under-filled and cut tasks to 35 tok/s. Set -ngl / --n-cpu-moe by hand. --n-cpu-moe 0 counts as unset.
- "Shared GPU memory under 0.3 GB" is not a usable target: the Windows counter also counts the CPU-side expert weights
  (llama-server shows 6-13 GB shared even at the fastest settings). Judge by tok/s and dedicated usage instead.
- test-models.ps1 max_tokens 600: thinking models (coder, mentor) sometimes use all 600 on reasoning, so the answer column
  is empty. Speed is still valid. Use a longer max_tokens to read answers.
- curl / Python requests from the cloud sandbox to huggingface.co are blocked. Query HF from the PC.
- Edge and Chrome are not installed. Launch via pywebview (app.py).
- C:\Users\zezu1\AppData\Local\Microsoft\WindowsApps\pythonw.exe is a Store stub without pywebview. Use the pythoncore-3.14-64 path.
- PowerShell -File with a [string[]] param only takes the first value. Use & 'script.ps1' -Models a,b,c.

# Atlas — integrated roadmap and release gates

## Architecture decision

Keep Atlas as one product and repository with separately deployable services. Do not merge the control plane into the desktop process. The control plane is integrated into the Atlas source tree, while running as its own Rust service. This preserves the desktop lifecycle boundary and lets the network service scale independently.

- React + TypeScript: Desktop presentation and interaction.
- Rust/Tauri: Desktop lifecycle, node supervisor, local resource limits, signing, Docker process ownership and native APIs.
- Python: existing Atlas Chat API/MCP compatibility and model tooling; retain where it preserves working integrations.
- Rust/Axum: network control plane.
- PostgreSQL: network identities, workload queue, node heartbeat state and contribution receipts.
- llama-swap/Ollama adapters: local inference provider compatibility.

## Completed in this delivery

- Added Rust/Axum control-plane service under `services/atlas-control-plane`.
- Added PostgreSQL schema/migrations, challenge-response Ed25519 registration, signed node request verification, replay fingerprints, heartbeats, node eligibility checks, scheduler-signed workload envelopes, receipt signature validation, operator node revocation and manual contribution review.
- Added localhost-only Docker Compose deployment and key-generation binary.
- Connected desktop heartbeat consent reporting to the server contract.
- Improved local model discovery and benchmarking to support both Ollama `/api/*` and OpenAI-compatible `/v1/*` endpoints, defaulting new profiles to the existing llama-swap port 8080.
- Improved Docker workload cancellation by recording the container ID file and stopping the container itself before terminating its owned CLI process.
- Preserved the existing chat iframe, Python API, data files and plugin-manager architecture.

## Still required before Atlas can be called complete

### Desktop and node
- Compile Tauri/Rust on Windows and fix any platform-specific compiler/runtime issues.
- Run the actual React production build and packaged NSIS/MSI build.
- Verify RX 9070 XT telemetry and llama-swap model benchmark on the user's PC.
- Verify Docker Desktop isolation, CPU/RAM enforcement, stop-on-consent-revocation and startup recovery.
- Implement GPU passthrough safely for approved worker images.
- Replace raw private-key file storage with Windows DPAPI-backed protected storage and platform ACLs.

### Network and distributed inference
- Add inference worker claim/result/stream protocol and node-side inference execution.
- Add compatibility-aware model placement and scheduling using GPU VRAM, RAM, model quantization, context length, throughput, bandwidth and node health.
- Add model transfer/cache integrity, backpressure, cancellation and node failure recovery.
- Add independent proof/verification strategy; node-signed receipts alone do not prove work was honestly performed.
- Add signed settlement statements and auditable contributor balances.

### Commercial production
- Customer identity, API keys, scopes, quotas and rate limiting.
- Subscription and payment provider integration, tax/invoice handling, refunds and chargebacks.
- Contributor payout/KYC compliance only when the business/legal model is defined.
- Public TLS ingress, WAF/rate limits, secret manager, backups, monitoring, incident response, abuse controls and penetration test.

## Non-negotiable safety gates

- Node participation and remote execution are separate opt-ins.
- A node's off switch stops accepting new work and terminates its owned active container.
- No global process-name kills; only processes/containers created by Atlas are stopped.
- No network or host mounts in default sandbox workloads.
- Immutable image digests only; no `latest` tags.
- Never call an execution receipt a verified contribution until independent evidence has been reviewed.
- No public endpoint, customer API sale or payment collection until the public control plane and commercial safeguards are complete.

# Atlas Chat — Project Master Document
**Document date:** 8 November 2026  
**Status:** Living founder / engineering source of truth  
**Project phase:** Active development; pre-release; fundraising narrative is exploratory

## 1. Executive summary

Atlas Chat is being developed as a local-first AI desktop application with a longer-term ambition to become a hybrid AI platform. The product thesis is that powerful AI should not be confined to centralized cloud interfaces or datacentre infrastructure. Atlas seeks to bring together local inference, model/tool access, agent workflows, operational visibility and, over time, distributed compute and a broader developer/community ecosystem.

The desktop application is the practical product foundation. The broader platform is a strategic direction, not a claim that every planned service is already operational.

## 2. Vision, mission and product thesis

**Vision:** Make capable, controllable AI infrastructure accessible to individuals and organizations, including through hardware they already own.

**Mission:** Build a coherent desktop-to-platform experience for running models, coordinating agents, connecting tools and observing execution.

**Core thesis:** Local compute can improve user control, reduce dependence on centralized inference for suitable workloads, and create a foundation for optional hybrid and distributed execution. The product must prove that this can be delivered with a simpler, safer and more useful user experience than assembling separate tools.

### Product principles
- Local-first by default where technically practical.
- Hybrid connectivity is optional and explicit.
- User data and existing workflows must be preserved during upgrades.
- Agent execution must be observable, attributable and auditable.
- Privileged operations require scoped approval.
- Reliability and end-to-end validation outrank feature-count claims.
- Desktop and online products remain distinct, with deliberate integration boundaries.

## 3. Product definition

### Near-term product: Atlas Desktop
A Windows desktop experience that brings together chat, local model access, tools, knowledge and developer/operations capabilities in one application.

### Longer-term platform: Atlas Network / ecosystem (working concept)
Potential platform capabilities include node registration, distributed workload scheduling, contribution verification, workload consent, centralized coordination and commercial APIs/services. These are roadmap concepts unless separately demonstrated and accepted.

### User groups to validate
1. Individuals who want local AI and control over their data.
2. Developers who need model-powered tools, agent workflows and local automation.
3. Technical teams that need governed agent execution and observability.
4. Potential compute contributors or node operators, if distributed execution proves viable.

These are target hypotheses, not validated customer segments.

### Desktop and application layer

- MCP host/tool integration, tool discovery, invocation, audit and approval boundaries.
- Knowledge Library, document ingestion and conversation import workflows.

### Agent and platform layer
- Atlas Node integration and hardware/runtime reporting.
- Operations dashboard for status, queue and audit visibility.
- Agent registry/telemetry concepts: identity, parent-child relationships, host/PID, task state, heartbeats, logs, traces and metrics.
- Dev Engine for local model-assisted development with isolated workspaces and reviewable patch proposals.

# Atlas Node Gateway Contract v0.2

The desktop client is deliberately a client of the commercial Atlas gateway. Do not expose the existing Atlas Chat localhost API as this service. All non-loopback traffic must use HTTPS.

## Identity and registration

1. `POST /v1/nodes/challenge`
   - Request: `{ "node_id": "<sha256-hex-of-ed25519-public-key>", "public_key_hex": "<32-byte-ed25519-public-key-hex>" }`
   - Response: `{ "challenge": "<cryptographically-random-single-use-nonce>", "expires_at_unix": 0 }`
   - Server stores challenge against the public key for at most 60 seconds, one use only.
2. `POST /v1/nodes/register`
   - Request: node_id, public_key_hex, challenge, signature_hex.
   - Signature is Ed25519 over the exact UTF-8 challenge bytes.
   - Server recomputes SHA-256(public key), checks challenge ownership/expiry/one-use, then issues a high-entropy revocable node token.
   - Response: `{ "node_token": "<opaque-secret>" }`.

## Signed node requests

Every authenticated POST uses bearer node token plus:

- `x-atlas-node-id`
- `x-atlas-timestamp` (Unix seconds)
- `x-atlas-signature` (Ed25519 signature hex)

Signed bytes are UTF-8:

`{timestamp}.{HTTP_METHOD}.{path}.{lowercase_hex_sha256_of_exact_compact_JSON_body}`

The server must enforce a narrow clock-skew window, one-time/replay protection for mutating operations, body-size limits, token revocation, node status and consent, per-node rate limits, and constant-time token comparison. JSON must be compactly serialized with lexicographically ordered object keys to match serde_json's canonical Value serialization used by the client.

## Node lifecycle and workloads

- `POST /v1/nodes/heartbeat` — signed device status and hardware capacity; heartbeat expiry marks a node unavailable.
- `POST /v1/workloads/claim` — signed claim request; returns HTTP 204 when no work is available or `{ "workload": <signed envelope> }`.
- Workload envelope fields: `workload_id`, `image`, `command`, `max_memory_mb`, `max_cpu_percent`, `expires_at_unix`, `nonce`, `signature_hex`.
- Workload signature is Ed25519 over compact lexicographically ordered JSON of all envelope fields except `signature_hex`, signed by the configured trusted scheduler key.
- `POST /v1/workloads/complete` — signed request carrying the node-signed execution receipt.

The scheduler must never send arbitrary host paths, mounts, host commands, secrets or network privileges. Images must be immutable SHA-256 digests and separately allowlisted by the device owner. Rejected, expired, untrusted or non-allowlisted jobs must never execute.

## Distributed inference

- `GET /v1/network/status` — public health/capacity summary only; no private node metadata.
- `POST /v1/inference` — signed, authenticated inference request. The platform chooses compatible online nodes based on model, VRAM/RAM, context size, quantization, queue depth, network latency and node consent. It returns a request/job identifier and a streamable result contract; the initial desktop client currently expects a JSON response. Add a streaming response contract before claiming production streaming support.

The scheduler should support whole-model placement first. Tensor/pipeline splitting across home PCs is a later capability because bandwidth and latency can make it slower than single-node inference.

## Contribution accounting

- `POST /v1/workloads/complete` stores a signed node assertion but must not immediately credit money.
- A verifier independently validates job assignment, nonce, time window, model/runtime, output or task-specific proof, resource limits and duplicate submission.
- `POST /v1/contributions/settlement` (server-side signed settlement) records accepted units, rate, adjustments, period, and verifier identity.
- A client must label locally signed receipts `EXECUTED_UNVERIFIED`. Only a platform-signed settlement response from a pinned trusted verifier key may be displayed as verified/earnings eligible.

A node signature is not proof of correct computation. GPU inference generally needs task-level validation, redundancy/spot checks or other verification before payouts. Do not describe self-reported GPU time as cryptographically proven work.

## Missing platform implementation

These endpoints, database tables, scheduler, inference router, independent verifier, settlement ledger, customer billing and payment processing are not implemented by the desktop package. They are the next server-side workstream. The desktop code does not silently emulate their success.
